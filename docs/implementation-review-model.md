# 実装・レビュー・修正を記録する設計

この文書は、1件の開発作業を「実装する、レビューする、必要なら修正する」という流れで進めるとき、
何を記録し、いつ次の作業へ進み、いつ完了にするかを決める。

後から履歴を見た人が、誰が何を行い、なぜ次の作業が必要になったかを追えることを目的とする。
ここでは記録と判断の規則を決める。Rustの型、SQLiteの変更、レビュー用のAIやworkspaceの実装は扱わない。

## この文書で決めること

- 実装、レビュー、修正を、1件の開発作業の中でどう区別して記録するか
- 失敗後の再試行と、レビュー指摘後の修正をどう区別するか
- レビュー結果をどう扱い、どの時点で作業を完了にできるか
- 後続の実装が保存すべき履歴と、既存の履歴を移行するときの扱い

## 用語

| この文書での言葉 | 意味 |
| --- | --- |
| 作業 | 利用者から依頼された、完了まで追跡する1件の開発依頼 |
| 実行 | 担当者が開始から結果確定まで行う1回分の処理。初回実装、その成果物のレビュー、レビュー後の修正は、それぞれ別の実行として履歴に残す |
| 初回実装 | 作業で最初に行う実装 |
| 再試行 | 実行が失敗したため、同じ実行先でもう一度行うこと |
| 切り替え再試行 | 実行が失敗したため、別のProviderまたはModelへ切り替えて行うこと |
| レビュー | 現在の成果物を確認し、承認・修正要求・判断不能のいずれかを返すこと |
| 修正 | レビューで修正を求められた後に、実装担当が成果物を直すこと |
| 現在の成果物 | 作業内で最後に成功した実装または修正が作った成果物 |

## 基本の流れ

通常は、次の順に進む。

```text
初回実装 → レビュー → 承認 → 作業完了
                     └→ 修正 → 再レビュー → 承認 → 作業完了
```

実装やレビューの実行が技術的に失敗した場合は、同じ実行先で再試行するか、別の実行先へ切り替えて
再試行する。これはレビューで修正を求められた場合とは別の流れである。

| 起きたこと | 次に行うこと | 記録する理由 |
| --- | --- | --- |
| 初回実装が成功した | 現在の成果物をレビューする | 何をレビューしたかを追えるようにする |
| 実行が失敗した | 再試行または切り替え再試行を判断する | 失敗への対応であることを残す |
| レビューで修正を求められた | 修正を行う | どの指摘を受けて直したかを残す |
| レビューで承認された | ほかの完了条件を確認して完了にする | 現在の成果物が承認済みであることを確認する |
| レビューで判断できなかった | あらためてレビューするか判断する | 修正要求と区別する |

## 何を実行ごとに残すか

実行ごとに、少なくとも次の情報を残す。

| 情報 | 内容 |
| --- | --- |
| 履歴番号 | 初回実装を1、そのレビューを2、レビュー後の修正を3のように、同じ開発依頼の中で実行を行った順に付ける番号 |
| 担当 | 実装担当か、レビュー担当か |
| 行った理由 | 初回実装、再試行、切り替え再試行、レビュー、修正のどれか |
| 関係する過去の実行 | 再試行なら失敗した実行、レビューなら対象の実装、修正なら修正要求を出したレビュー |
| 実行の状態 | 実行中、成功、失敗、取消のどれか |
| 結果 | 実装結果、検証結果、利用量、レビュー結果など |

実装と修正は、どちらも実装担当が行う。修正だけを別の担当として扱わない。これにより、実装担当の
実績をまとめて確認でき、同時に「どのレビューを受けて修正したか」も履歴から分かる。

## 守る規則

### 実行の順番

1. 初回実装は、1件の作業につき1回だけである。作業内で最初の実行であり、過去の実行を参照しない。
2. 初回実装以外の実行は、同じ作業内にある過去の実行を参照する。ただし、移行した履歴で関係を復元できない実行は例外とする。この実行は履歴番号と担当を残し、参照先を空にして関係を不明のまま保存する。
3. 実行中の処理がある間は、次の実行を始めない。並列に進めることはこの設計の対象外とする。
4. 過去の履歴を後から書き換えない。新しい判断は新しい実行として残す。

### 担当と行った理由

- 初回実装と、レビューで修正を求められた後の修正は、実装担当が行う。
- 失敗後の再試行と切り替え再試行は、失敗した実行と同じ担当が行う。
- レビューはレビュー担当が行い、成功した実装または修正を対象にする。
- レビュー結果を保存できるのは、レビュー担当による実行だけである。

### 失敗後の扱い

- 再試行は、失敗した実行と同じProvider / Modelを使う。
- 切り替え再試行は、失敗した実行とは異なるProviderまたはModelを使う。
- どちらも、失敗した実行を参照する。レビュー指摘を受けた修正として扱わない。

### レビューと修正

- レビューは、現在の成果物だけを対象にする。古い成果物を後から承認対象にしない。
- 修正は、修正を始める時点の現在の成果物を対象にして「修正要求」を出した、成功済みのレビューを参照する。
  同じ成果物に対して後から「判断不能」のレビューがあっても、その修正要求を参照してよい。
- 修正が成功すると、その修正後の成果物が新しい「現在の成果物」になる。以前の承認は、その後の完了判定には使えない。

## レビュー結果、監督判断、完了

レビューには、次の3種類の結果がある。

| 結果 | 意味 | 次の扱い |
| --- | --- | --- |
| 承認 | 現在の成果物を受け入れた | ほかの完了条件も満たせば作業を完了にできる |
| 修正要求 | 直すべき点がある | 作業を継続し、修正を行う |
| 判断不能 | 承認か修正要求かを確定できない | 作業を継続し、次のレビューを判断する |

レビュー担当が有効なレビュー結果を返せたなら、レビューという処理自体は成功である。結果が「修正要求」
であっても、レビューの実行が失敗したことにはならない。反対に、レビュー結果が欠けている、または形式が
不正なら、そのレビュー実行は失敗として扱い、再試行または切り替え再試行の対象にする。

review の承認は reviewer の見解であり、監督Codexの受入ではない。作業を完了にするには、監督Codexが
現在の成果物、必要な検証、必要ならreview・CI・公開の証拠を評価して受入を記録し、Operation Service が
完了条件を確定する必要がある。承認の後に成果物が変わった場合は、古いreview・検証・受入を新しい成果物へ
流用しない。

## 履歴の例

レビューで修正を求められ、修正後に承認される場合は、次の履歴になる。

| 順番 | 担当 | 行ったこと | 結果 |
| --- | --- | --- | --- |
| 1 | 実装担当 | 初回実装 | 成功 |
| 2 | レビュー担当 | 1の成果物をレビュー | 修正要求。レビュー処理は成功 |
| 3 | 実装担当 | 2の修正要求を受けて修正 | 成功 |
| 4 | レビュー担当 | 3の成果物をレビュー | 承認。レビュー処理は成功 |

別のProvider / Modelへ切り替えて再試行する場合は、次のようになる。

| 順番 | 担当 | 行ったこと | 結果 |
| --- | --- | --- | --- |
| 1 | 実装担当 | 初回実装 | 失敗 |
| 2 | 実装担当 | 1の失敗を受け、別の実行先で再試行 | 成功 |

この2番目の実行は、レビュー後の修正ではない。

## 状態の扱い

Attempt はモデル呼び出しの状態だけを表す。`Succeeded` は呼び出しが正常終了した意味であり、検証成功や
review承認を含まない。Validation は成果物に結び付く別事実である。作業は、実行中だけでなく、検証・
レビュー・修正・監督Codexの次の判断を待つ間も「処理中」とする。実行できる次の処理がなく、監督Codexが
進められないと判断したときだけ作業を失敗にする。詳細は[ドメインモデル](domain-model.md)を正本とする。

## 成果物の受け渡し

レビュー担当には、対象となる実装または修正が作った正確な成果物を、読み取り専用で渡す。レビュー担当は
対象の成果物を変更しない。修正は、レビュー対象だった成果物を出発点にする。

どのworktreeを使うか、同じworktreeを再利用するか、別の場所に成果物を展開するかは、実行環境を作る
仕組みの責任とする。この設計では、pathやbranchではなく履歴上の参照で対象を特定する。

## 保存と移行

履歴は実行ごとに保存する。実行の保存先には、順番、担当、行った理由、参照先の実行IDを持たせる。
レビュー結果は、レビュー実行に対して最大1件保存する。

既存の履歴を移行するときは、次のように扱う。

- 担当は、既存の作業にある担当情報から引き継ぐ。
- 最初の実行は初回実装として扱う。
- 2回目以降の実行が再試行、切り替え再試行、レビュー、修正のどれだったかは、既存データから判断できない。
  この場合は、履歴番号と担当は引き継ぐ一方、参照先を空にして関係だけを「不明」として保存する。推測で補わない。

## モデルの選定との関係

モデルを選ぶ仕組みは、実装担当またはレビュー担当に対して実行先を提案する。実行先を決めることと、
その実行が初回実装・再試行・レビュー・修正のどれなのかを決めることは別である。

実行の種類と参照先は、作業の履歴を確認した実行管理側が決める。モデルを選ぶ仕組みが、履歴の関係を
直接書き換えたり、勝手に確定したりしない。

## 実装で使う名前

ここからは、後続実装で本文の言葉をデータへ対応づけるための定義である。本文を読むために覚える必要はない。

| 本文の言葉 | 実装上の名前 |
| --- | --- |
| 作業 | `Task` |
| 実行 | `Attempt` |
| 実装担当 | `implementer` |
| レビュー担当 | `reviewer` |
| 初回実装 | `Initial` |
| 再試行 | `RetryOf` |
| 切り替え再試行 | `EscalationOf` |
| レビュー | `ReviewOf` |
| 修正 | `ReworkFrom` |
| 移行時に関係が不明 | `LegacyUnspecified` |

実装上の関係には、次の組み合わせだけを許可する。

| 実装上の関係 | 担当 | 参照先 |
| --- | --- | --- |
| `Initial` | `implementer` | なし |
| `RetryOf` | 参照先と同じ担当 | 失敗または再試行可能な取消となった実行 |
| `EscalationOf` | 参照先と同じ担当 | 失敗または再試行可能な取消となった実行 |
| `ReviewOf` | `reviewer` | 現在の成果物を作った、成功済みの実装担当の実行 |
| `ReworkFrom` | `implementer` | 現在の成果物への修正要求を返した、成功済みのレビュー担当の実行 |
| `LegacyUnspecified` | 移行前の担当を引き継ぐ | なし |

実行の保存先には、履歴番号、担当、関係の種類、参照先の実行IDを持たせる。実装上の列名は
`sequence`、`role`、`relation_kind`、`related_attempt_id`とする。履歴番号は作業ごとに重複させない。

レビュー結果は別の保存先に、作業ID、実行ID、対象成果物ID、結果、要約を保存する。作業IDと実行IDの組は一意とする。
監督Codexの受入はreview結果と別の保存先に、対象成果物ID、`accepted` / `rejected` /
`changes_requested`、理由、参照した証拠を保存する。
移行時に関係が不明な実行は、`legacy_unspecified`として保存し、`related_attempt_id`を持たない。

## 後続実装と対象外

後続の実装では、ここで定めた履歴の規則をDomain、Ledger、モデル選定、実行環境の順に適用する。
Provider / Modelの選定、AIレビューProvider、レビュー・修正用workspace、複数実行の並列化、
integration branch、merge、cherry-pickの実装は、この文書の対象外である。
