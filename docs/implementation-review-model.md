# 実装・レビュー・修正を記録する設計

まず[開発支援システムの全体像](architecture.md)を読み、利用者、監督Codex、Rust側の役割を確認してください。本書では、その構成の中で一つの開発作業に属する実装、レビュー、修正をどう記録し、次の処理へ進むかを定めます。

本書では、実行の担当と理由、過去Attemptとの関係、レビューが任意であること、Taskを完了にする判断、既存履歴の移行方法を説明します。後から履歴を読む人が、誰が何を行い、なぜ次へ進んだのかを追えるようにすることが目的です。Rustの型やSQLiteの実装、AIレビューやworkspaceの構成は決めません。

## この文書で決めること

- 実装、レビュー、修正を、1件の開発作業の中でどう区別して記録するか
- 失敗後の再試行と、レビュー指摘後の修正をどう区別するか
- レビュー結果をどう扱い、どの時点で作業を完了にできるか
- 後続の実装が保存すべき履歴と、既存の履歴を移行するときの扱い

## なぜ実行同士の関係を記録するのか

同じ作業でモデルを複数回呼び出すと、順番だけでは各実行が何を受けて始まったのか分かりません。たとえば「実装担当をもう一度呼んだ」という記録だけでは、前のモデル呼び出しが失敗したのでやり直したのか、正常に作られた成果物に問題が見つかったので直したのかを区別できません。両者では確認すべき失敗と、次に渡す入力が違います。

そこで、1回ごとの実行に「関係の種類」と「関係する過去の実行」を記録します。この組を **履歴上の関係（relation）** と呼びます。初回実装など、参照する過去の実行がない場合もあります。入力のcommitや成果物は入力欄に保存し、関係の記録に重ねて保存しません。

たとえば、実装1が成果物Aを作り、レビュー2がAに修正を求め、実装3がそれを直して成果物Bを作ったとします。

```text
実装1 ── 成果物Aを作る
  ↑
レビュー2 ── 実装1の成果物を確認して修正を求める（ReviewOf → 実装1）
  ↑
実装3 ── レビュー2の指摘に基づいて直す（ReworkFrom → レビュー2）
```

この関係を記録すれば、実装3を確認する人はレビュー2へ戻り、どの指摘に対応したのかを調べられます。単に直前の実行を参照する仕組みではありません。途中に別のレビューが入っても、修正対象の指摘を出したレビューを特定します。

| 確認したいこと | 関係の記録をどう使うか | 区別できないと起きる問題 |
| --- | --- | --- |
| もう一度モデルを呼んだのは、実行失敗への対応か、成果物の修正か | 再試行の対象となった実行、または修正要求を出したレビューへ戻る | モデル呼び出しの失敗と成果物の不備を混同し、確認する原因や次に使う入力を取り違える |
| 修正はどの指摘への対応か | 修正から対象レビューへ戻り、指摘と修正内容を照らし合わせる | 別のレビューへの対応を今回の修正だと思い込み、未対応の指摘を見落とす |
| レビューはどの実装の成果物に対して行ったか | レビューから作成元の実行へ戻り、レビュー結果の対象成果物も確認する | 成果物Aへの承認を、後で作られた成果物Bへの承認として扱ってしまう |
| レビューをせずに次の実行へ渡した入力はどこから来たか | 入力の成果物と、記録されている同じ作業内の作成元を確認する | レビュー指摘を受けた修正だと推測したり、入力の出どころを見失ったりする |

**関係の記録だけで、成果物が正しい、指摘を直せた、作業を完了できるとは判断しません**。 指摘への対応は実際の差分と検証結果で確認します。レビューの有効性や完了条件は、対象成果物に結び付いたレビュー結果・検証結果・監督Codexの判断を照合します。関係は、その確認に必要な過去の実行へ戻るための記録です。

関係の種類は自由記述の理由文ではありません。記録できる事実を分類するためのものであり、分からない動機を推測して補いません。一般の実行要求に再試行やレビュー指摘への修正という指定がない場合は、後述の`SpecifiedInput`として入力と分かっている作成元を保持します。監督Codexが成果物を採用する理由は、別の監督判断に記録します。

## 用語

| この文書での言葉 | 意味 |
| --- | --- |
| 作業（Task） | 利用者から依頼され、完了まで追跡する開発依頼 |
| 実行（Attempt） | Provider / Modelへ依頼した1回分の呼び出し。実装、レビュー、修正はそれぞれ別のAttemptとして記録する |
| 初回実装（Initial） | 作業内のsequence 1で、BaseInputから開始する実装担当の実行 |
| 再試行（RetryOf） | 失敗した実行、または再試行が許可された取消の実行と同じ担当が、同じProvider / Modelで再試行すること |
| 切り替え再試行（EscalationOf） | 失敗した実行、または再試行が許可された取消の実行と同じ担当が、別のProviderまたはModelへ切り替えて再試行すること |
| 成功済みの作成Attemptを対象にするレビュー（ReviewOf） | 現在の成果物を確認し、承認・修正要求・判断不能を返す実行 |
| レビュー指摘への修正（ReworkFrom） | レビューで修正を求められた後、実装担当が成果物を直すこと |
| 現在の成果物 | 作業内で最後に成功した実装または修正が作った成果物 |
| 指定入力からの実行（SpecifiedInput） | 既存の理由分類に当てはまらない入力を使う実行。ArtifactInputに同じTask内の作成元Attemptが記録されていれば、その参照を保持する |
| 移行時の関係不明（LegacyUnspecified） | 既存履歴を移す際、理由や参照先を復元できない記録の分類 |

## 基本の流れ

実装が成功した後、監督Codexは検証結果と成果物を確認し、AIレビューを行うか判断します。レビューは任意で、実施する場合と省略する場合の両方があります。

```text
実装 → 必要な検証・成果物の確認
        ├→ AIレビューを省略 → 監督Codexの採用判断 → ほかの完了条件を確認 → 作業完了
        └→ AIレビューを実施
              ├→ 承認 → 監督Codexの採用判断 → ほかの完了条件を確認 → 作業完了
              ├→ 修正要求 → 修正 → 新しい成果物を検証・確認し、次の判断へ
              └→ 判断不能 → 判断材料を確認し、再レビューなどの次の操作を判断
```

レビューを省略しても、検証や監督Codexによる採用判断を省略する意味ではありません。必要なCI・公開結果なども確認し、Operation Serviceが完了条件を確定します。また、レビュー後の修正に限らず、検証で見つかった問題をレビューなしで次の実装担当へ渡して直すこともできます。

実装やレビューの呼び出し自体が失敗した場合は、同じ実行先で再試行するか、別の実行先へ切り替えて再試行します。これは、呼び出しは成功したが検証に失敗した場合や、レビューで修正を求められた場合とは別の流れです。

| 起きたこと | 次に行うこと | その記録が判断に必要な理由 |
| --- | --- | --- |
| 初回実装が成功した | 成果物を検証・確認し、AIレビューを行うか判断する | モデル呼び出しの成功と、成果物が要求を満たすことは別だから。作成元と成果物を特定し、以後の検証や判断が同じ成果物を対象にしているか確認する |
| AIレビューを省略した | 必要な検証結果などから監督Codexが採否を判断する | AIの承認が存在しない場合でも、何を根拠にどの成果物を採用したか説明できるようにする。レビューなしを承認済みという記録に置き換えない |
| モデル呼び出しが失敗した | 再試行または切り替え再試行を判断する | どの実行の失敗に対応したかを特定し、成果物の修正と混同せず、再試行対象と実行先の条件を確認する |
| 検証で成果物の問題が見つかった | 指定した成果物から修正し、修正後を改めて検証する | モデル呼び出しは成功していても成果物には問題があると区別する。修正前の検証結果を修正後の成果物へ流用しない |
| レビューで修正を求められた | 対象成果物を修正する | 修正がどの指摘への対応かを照合し、別のレビューへの対応や未対応の指摘を取り違えないようにする |
| レビューで承認された | 監督Codexが採否を判断し、ほかの完了条件を確認する | 承認が現在の成果物に対するものか確認する。古い成果物の承認やAIの見解だけで、現在の作業を完了にしない |
| レビューで判断できなかった | 判断材料を確認し、あらためてレビューするか判断する | 承認や修正要求が確定していないため、その結果を採用の根拠や修正指示として読み替えない |

この表は各記録を何のために確認するかを示しています。すべての記録をrelation欄へ保存するという意味ではありません。実行同士の関係はAttemptに、検証はValidationに、AIの見解はレビュー結果に、監督Codexの採否と理由は監督判断に分けて記録します。レビューを省略したという架空のAttemptやレビュー結果は作りません。

## 何を実行ごとに残すか

Attemptごとに、少なくとも次の情報を記録します。

| 情報 | 内容 |
| --- | --- |
| 履歴番号 | Task内の順番。`sequence 1`は最初のAttemptを表す。初回実装になるのは、sequence 1が実装担当でBaseInputを使う場合だけ |
| 担当（role） | 実装担当（実装担当）、レビュー担当（レビュー担当）、調査担当（調査担当）など、実行時に指定された役割 |
| 理由（relation kind） | `Initial`、`RetryOf`、`EscalationOf`、`ReviewOf`、`ReworkFrom`、`SpecifiedInput`のいずれか。移行時に関係を復元できない旧記録は`LegacyUnspecified`とする |
| 参照先（related attempt） | `RetryOf`などの既存の理由に必要なAttempt、または`SpecifiedInput`のArtifactInputに記録された同じTask内の作成元Attempt。理由が不明でも作成元が分かるなら参照を保持する。BaseInputと作成元不明の場合は参照先なし |
| 実行の状態 | 実行中、成功、失敗、取消のどれか |
| 結果 | モデル呼び出しの終了結果、AgentResult（モデルの作業報告）、利用量など。検証結果とレビューの結論は別の記録に保存する |

実装担当が実装と修正を行います。修正専用のroleは設けません。実装担当の履歴をまとめて確認でき、`ReworkFrom`の場合は、どのレビュー指摘に基づく修正かも追えます。

## 守る規則

### 実行の順番

1. `Initial`はTask内sequence 1でBaseInputから始める実装担当だけに一度付けます。sequence 1が調査担当など別roleの場合や、ArtifactInputから始まる場合は`SpecifiedInput`です。後続の実装担当を`Initial`に戻しません。
2. `Initial`以外の新規実行で既存の理由分類が当てはまらない場合は、`SpecifiedInput`を使います。ArtifactInputに同じTask内の作成元Attemptが記録されていれば、そのAttemptを参照します。BaseInputと作成元不明のArtifactInputには参照先を設定しません。`LegacyUnspecified`は、既存履歴を移す際に関係を復元できない場合だけ使います。
3. 実行中の処理がある間は、次の実行を始めない。並列に進めることはこの設計の対象外とする。
4. 過去の履歴を後から書き換えない。新しい判断は新しい実行として残す。

### 担当と行った理由

- `Initial`と、`ReworkFrom`に基づきレビューで修正を求められた後の修正は、実装担当が行う。一般の明示入力による修正はこの条件に含めず、既存の理由分類がなければ`SpecifiedInput`とする。
- 再試行と切り替え再試行は、失敗した実行、または再試行が許可された取消の実行を対象にし、参照先と同じ担当が行います。取消されたという理由だけで、再試行を許可しません。
- `ReviewOf`は、現在Artifactを作った成功済み実装担当 Attemptが確認できる場合に使います。一般のレビューは現在Artifactを対象にできます。作成元Attemptが不明なら`SpecifiedInput`とし、推定した参照先は付けません。ArtifactInputに同じTaskの作成元Attemptが記録されている場合は、その参照を`SpecifiedInput`にも保持します。
- レビュー結果を保存できるのは、レビュー担当による実行だけです。
- レビューを行うかは監督Codexが判断する。修正やTask完了にレビューを必須としない。

### 再試行の扱い

対象は、失敗した実行、または再試行が許可された取消の実行です。以下では、この対象を「参照先」と呼びます。

- 再試行は、参照先と同じProvider / Modelを使います。
- 切り替え再試行は、参照先とは異なるProviderまたはModelを使います。
- どちらも、その対象の実行を参照します。レビュー指摘を受けた修正として扱いません。

### レビューと修正

- レビューの対象は現在の成果物です。古い成果物を後から承認対象にしません。
- `ReworkFrom`による修正は、現在の成果物に「修正要求」を出した成功済みレビューを参照します。同じ成果物に対して後から「判断不能」のレビューがあっても、修正要求を参照できます。
- 一般の`SpecifiedInput`による修正には、上記のレビュー参照条件を適用しません。明示されたArtifactInputを出発点にします。
- 修正が成功すると、修正後の成果物が新しい現在の成果物になります。以前の承認を、その後の完了判断に流用しません。

## レビュー結果、監督判断、完了

レビュー結果は次の3種類です。

| 結果 | 意味 | 次の扱い |
| --- | --- | --- |
| 承認 | 現在の成果物を受け入れた | ほかの完了条件も満たせば作業を完了にできる |
| 修正要求 | 直すべき点がある | 作業を継続し、修正を行う |
| 判断不能 | 承認か修正要求かを確定できない | 作業を継続し、次のレビューを判断する |

有効なレビュー結果が返った場合、レビュー処理自体は成功です。「修正要求」という結果でも、レビュー実行の失敗ではありません。結果が欠けている、または形式が不正な場合はレビュー実行を失敗として扱い、再試行または切り替え再試行の対象にします。

レビューの承認はレビュー担当の見解であり、監督Codexによる受入を意味しません。Taskを完了するには、監督Codexが現在の成果物と必要な検証結果を評価し、必要に応じてレビュー、CI、公開結果も確認して受入を記録します。Operation Serviceが完了条件を確定します。

レビューは任意です。監督Codexはレビュー証拠がなくても成果物を判断できます。ほかの完了条件を満たしていれば、Taskを完了できます。承認後に成果物が変わった場合は、以前のレビュー、検証、受入を新しい成果物へ流用しません。

## 履歴の例

### AIレビューを省略して修正・完了判断へ進む例

初回実装が作った成果物Aをテストしたところ問題が見つかり、監督CodexがAIレビューなしで修正を依頼する場合です。

| 手順 | 行ったこと | 記録と確認する対象 |
| --- | --- | --- |
| 1 | 実装担当を呼び、成果物Aを作る | Attempt 1は`Initial`、参照先なし。モデル呼び出しは成功 |
| 2 | Aを検証し、問題を見つける | AへのValidationが失敗。Attempt 1を失敗へ書き換えない |
| 3 | Aを入力に、一般の実行要求で実装担当へ修正を依頼する | Attempt 2は`SpecifiedInput`。Aに記録された同じTask内の作成元Attempt 1を参照し、成果物Bを作る。存在しないレビューは参照しない |
| 4 | Bを検証し、成果物と結果を確認する | BへのValidationを記録。Aの検証結果をBの結果として扱わない |
| 5 | 監督CodexがBを採用し、ほかの完了条件を確認する | Bへの監督判断と必要な証拠を記録し、Operation Serviceが完了条件を確定する。AIレビュー結果は存在しない |

この例では、モデル呼び出しが失敗したから再試行したのではなく、正常に作られた成果物を直しています。また、一般の実行要求にはレビュー指摘への修正理由の指定がないため、`ReworkFrom`と推測せず、指定された入力と分かっている作成元を記録します。初回の成果物をそのまま採用できる場合は、手順3のモデル呼び出しを行わず、Aへの検証と監督判断から完了条件を確認します。

### AIレビューで修正を求められる例

レビューで修正を求められ、修正後に承認される場合は、次の履歴になる。

| 順番 | 担当 | 行ったこと | 関係と参照先 | 結果 |
| --- | --- | --- | --- | --- |
| 1 | 実装担当 | BaseInputから初回実装 | `Initial`、参照先なし | 成功 |
| 2 | レビュー担当 | 1が作った成果物をレビュー | `ReviewOf` → Attempt 1 | 修正要求。レビュー処理は成功 |
| 3 | 実装担当 | 2の修正要求を受けて修正 | `ReworkFrom` → Attempt 2 | 成功 |
| 4 | レビュー担当 | 3が作った成果物をレビュー | `ReviewOf` → Attempt 3 | 承認。レビュー処理は成功 |

別のProvider / Modelへ切り替えて再試行する場合は、次のようになる。

| 順番 | 担当 | 行ったこと | 関係と参照先 | 結果 |
| --- | --- | --- | --- | --- |
| 1 | 実装担当 | BaseInputから初回実装 | `Initial`、参照先なし | 失敗 |
| 2 | 実装担当 | 1の失敗を受け、別の実行先へ切り替えて再試行 | `EscalationOf` → Attempt 1 | 成功 |

この2番目の実行はレビュー後の修正ではなく、失敗後の切り替え再試行です。

## 状態の扱い

Attemptはモデル呼び出しの状態だけを表します。`Succeeded`は呼び出しが正常終了した意味で、検証成功やレビュー承認を含みません。ValidationはArtifactに結び付く別の記録です。

検証、レビュー、修正、監督Codexの次の判断を待っている間も、作業は「処理中」です。次に実行できる操作がなく、監督Codexが続行できないと判断した場合に作業を失敗にします。状態の詳しい定義は[ドメインモデル](domain-model.md)を参照してください。

## 成果物の受け渡し

`ReviewOf`では、レビュー担当へ成功済みの実装担当 Attemptが作った現在Artifactを読み取り専用で渡します。履歴では、その作成Attemptを参照します。

一般の`SpecifiedInput`によるレビューでは、要求された現在Artifactを読み取り専用で渡します。ArtifactInputに同じTask内の作成元Attemptが記録されていれば、その参照を履歴に保持します。レビュー担当はArtifactを変更しません。

`ReworkFrom`による修正はレビュー対象だったArtifactを出発点にします。一般の`SpecifiedInput`による修正は、明示されたArtifactInputを出発点にします。

どのworktree（作業ディレクトリ）を使うか、同じ場所を再利用するか、別の場所へArtifactを展開するかは、実行環境の責任です。この設計では、ファイルのパスやGitのブランチ名ではなく、履歴上のArtifact参照で対象を特定します。

## 保存と移行

履歴はAttemptごとに保存します。各行には順番、担当、行った理由、参照先のAttempt IDを記録します。レビュー結果は、1つのレビューのAttemptにつき最大1件です。

既存履歴を移行するときは、次の順に扱います。

- 既に保存された関係（relation）と参照先がある場合は、そのまま引き継ぎます。新規履歴の規則で再分類したり、参照先を置き換えたりしません。
- 担当（role）は既存の作業記録から引き継ぎます。
- 関係（relation）が保存されていない旧行を`Initial`へ分類できるのは、sequence 1、`role=implementer`、BaseInputのすべてを既存データで確認できる場合だけです。保存済みの関係はこの条件で再判定しません。
- 関係がない旧行について、既存データから分類や参照先を復元できない場合は、既存の履歴番号と担当を引き継いで`LegacyUnspecified`にします。`related_attempt_id`（参照Attempt ID）は設定しません。sequenceやroleを確認できない場合、またはsequence 1が実装担当でない場合に、新しい関係を推測しません。

## モデルの選定との関係

モデル選定は、実装担当またはレビュー担当に使うProvider / Model（実行先とモデル）を提案します。どのProvider / Modelを使うかという選定と、そのAttemptが初回実装・再試行・レビュー・修正のどれに当たるかは別の判断です。

Attemptの種類と参照先は、Taskの履歴や明示されたArtifactInputを確認する実行管理側が決めます。モデル選定は履歴のrelationを書き換えたり、入力にない再試行・修正理由を推測したりしません。

## 実装で使う名前

ここからは、本文で使った言葉を後続実装のデータへ対応づけるために定義します。本文を読むために覚える必要はありません。

| 意味 | 保存する値 |
| --- | --- |
| 作業 | `Task` |
| 1回のProvider / Model呼び出し | `Attempt` |
| 実装担当 | `implementer` |
| レビュー担当 | `reviewer` |
| 初回実装 | `Initial` |
| 再試行対象の実行と同じProvider / Modelで再試行 | `RetryOf` |
| 再試行対象の実行から別Provider / Modelへ切り替える | `EscalationOf` |
| 成功済みの作成Attemptを対象にするレビュー | `ReviewOf` |
| レビュー指摘に基づく修正 | `ReworkFrom` |
| 既存の理由分類が当てはまらない新規実行 | `SpecifiedInput` |
| 移行時に関係を復元できない旧履歴 | `LegacyUnspecified` |

実装上の関係には、次の組み合わせだけを許可する。

| 実装上の関係 | 担当 | 参照先 |
| --- | --- | --- |
| `Initial` | `implementer` | なし。Task内sequence 1のBaseInputによる実装担当だけ |
| `RetryOf` | 参照先と同じ担当 | 失敗または再試行が許可された取消となった実行 |
| `EscalationOf` | 参照先と同じ担当 | 失敗または再試行が許可された取消となった実行 |
| `ReviewOf` | `reviewer` | 現在の成果物を作った、成功済みの実装担当の実行 |
| `ReworkFrom` | `implementer` | 現在の成果物への修正要求を返した、成功済みのレビュー担当の実行 |
| `SpecifiedInput` | 実行時に指定された担当 | ArtifactInputに記録された、同じTask内の作成元Attemptが分かればそのAttempt。BaseInputまたは作成元不明ならなし |
| `LegacyUnspecified` | 移行前の担当を引き継ぐ | なし |

保存する関係には、履歴番号、担当、関係の種類、参照先の実行IDを含めます。実装上の列名は`sequence`、`role`、`relation_kind`、`related_attempt_id`です。履歴番号はTask内で重複させず、最初のAttemptをsequence 1とします。

新しい履歴を分類する規則は次のとおりです。

- `Initial`はTask内sequence 1のBaseInputから始める実装担当だけに使います。調査担当、レビュー担当、`Initial`に該当しないBaseInput（後続実行など）、レビューを経ていない修正、作成元Attemptが特定できない現在Artifactへのレビューなど、既存の理由分類に当てはまらない新規実行は`SpecifiedInput`です。
- `ReviewOf`は、現在Artifactの作成元が成功済み実装担当 Attemptだと確認できる場合に使います。それ以外の一般レビューは`SpecifiedInput`です。
- BaseInputを受け取るレビュー担当も`SpecifiedInput`です。Artifactを対象としない読取専用のAttemptとして扱い、ArtifactのReviewVerdictは作りません。
- `SpecifiedInput`の`related_attempt_id`には、ArtifactInputに記録された同じTask内の作成元Attemptを設定します。分類理由が分からなくても、既知の作成元参照を省略しません。BaseInputには参照先を設定せず、過去Artifactとcommitが一致しても関係を推定しません。
- `SpecifiedInput`は入力を二重保存する分類ではありません。BaseInputまたはArtifactInputの値は、既存のAttempt入力欄に一度だけ保存します。

一般の`attempt.run`要求には、retry/rework理由や参照Attemptを指定する入力項目がありません。そのためServiceやモデル選定は、Provider / Modelの違い、instruction、直前のValidationやレビューだけから`RetryOf`、`EscalationOf`、`ReworkFrom`を推定しません。これらの関係を明示的に受け付ける既存APIでは、現在の理由と参照先の検証を維持します。

`LegacyUnspecified`は、移行時に既存関係を復元できない場合だけに使います。新しいAttemptには使いません。

レビュー結果と監督Codexの判断は別々に保存します。

- ReviewVerdictにはTask ID、レビューのAttempt ID、対象Artifact ID、結果、要約を保存します。Task IDとAttempt IDの組は一意です。
- CodexDecisionには対象Artifact ID、`accepted` / `rejected` / `changes_requested`、理由、参照した証拠を保存します。
- 移行時は、保存済みrelationと参照先をそのまま保持します。relationがない旧行で理由や参照先を復元できない場合だけ`legacy_unspecified`（`LegacyUnspecified`）とし、`related_attempt_id`は設定しません。

## 後続実装と対象外

後続実装では、ここで定めた履歴規則をDomain、Ledger、モデル選定、実行環境へ反映します。

Provider / Model選定処理、AIレビュー用Provider、レビュー・修正用workspace、複数Attemptの並列実行は、この文書では実装しません。統合用ブランチ、マージ、コミット単位の取り込み（cherry-pick）も対象外です。
