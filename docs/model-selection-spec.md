# モデル選定の目的・流れ・判断規則

監督Codexが実装やレビューの担当モデルを選ぶとき、Rustが何を知らせ、監督Codexが何を判断し、Rustが何を確かめて実行するかを説明する。

## 読者・目的・範囲

[開発支援システムの全体像](architecture.md)を読んだ利用者と実装担当者が、モデル選定の分担と判断条件を確認するための概要である。正確なJSON項目・型・省略条件・例・Rust型案は[入力・出力詳細仕様](model-selection-spec-reference.md)にまとめる。MCPの操作概要と操作詳細を分ける構成に揃える。

Rustから監督Codexへ渡す情報と、その選定結果の形式はモデル選定仕様の対象である。実行先ごとのCLI/APIからの情報取得方法、モデル性能の評価方法、通信処理と選定処理の実装は扱わない。

この文書と詳細仕様は後続実装のための資料である。文書を追加・整理しただけで実行時の動作は変わらない。利用可能なモデルや料金を収集する本番処理、最も安いモデルを探す機能はまだ用意されていない。

## 最初に読む要約

- **Rust側が集めるもの:** 作業の要求、実行先とモデルの候補、利用可否、使用量や制約、保存済みの実行履歴。各情報には出どころと確認時刻を付ける。
- **監督Codexが返すもの:** 今回必要な担当ごとに、選んだ実行先・モデルと、その選定理由。観測値や過去の結果を書き換えて返すものではない。
- **Rust側が実行前に確かめるもの:** 候補に存在する組合せか、必要な能力があるか、利用可能か、設定された制約に反しないか。選定理由がもっともらしくても、検査を省略しない。

たとえば「実装担当を選ぶ」という要求に、Rust側が候補A・Bと既知の利用状況を渡し、監督Codexが「Aを選ぶ、理由は実装に必要な能力があるから」と返す。Rust側はAがまだ利用可能かを再確認して実行へ渡す。**候補情報を取れない場合に、Codexがモデル一覧や利用量を想像して補うことはない。**

## モデルを選んで実行する流れ

モデル選定では、Rustが収集・記録した事実に基づき、監督Codexが担当モデルを判断します。

1. Rust側が、作業の要求、候補、利用可否・制限・使用量・過去実績・実行履歴を、選定時点の記録（snapshot）として固定します。
2. 監督Codexがその記録を比較し、必要な担当ごとに実行先とモデル、選定理由を返します。
3. Rust側が選定結果を元の記録と最新の事実に照合し、実行してよいものだけを実行へ渡します。

```text
Rustが事実を収集 → JSON入力 → Codexが候補を選定 → JSON出力 → Rustが検証 → 実行
```

この仕様は選定用の入出力を定める。Providerごとの呼出し方、観測値を取得する処理、モデルの性能評価方法は定義しない。Rust型・JSON形式・接続処理・DB形式の実装変更も、この文書だけでは行わない。

ここでいうPlannerはモデルを選ぶ役割を指す。目標構成では監督Codexが判断する。現行CLI内部の`CodexPlanner`をMCP経路で自動的に起動するという意味ではない。

## 監督CodexとRust側の分担

| 情報・操作 | Rust側 | 監督Codex |
| --- | --- | --- |
| 要求と候補情報の収集・秘密情報の除外 | 収集し、出どころ・時刻とともに渡す | 書き換えずに受け取る |
| API使用量・設定予算・残量 | 取得・計算の根拠を保持する | 比較材料として使う |
| トークン数・費用の推定 | `estimated`と明示して渡す | 不確実性を考慮する |
| 過去実績・実行履歴 | DBから集計し、当時の記録を保持する | 次のモデル選定に使う |
| 担当ごとの実行先・モデル選定 | 候補と強制する制約を提示する | 選んだ組と理由を返す |
| Task・Attemptの状態変更 | ドメインのAPIを通して適用する | 選定結果から書き換えない |
| 実行前の再検証・制約の強制 | 検査し、違反は拒否する | 迂回できない |

選定結果は「この担当を選ぶ」という判断です。Operation Serviceは、実行の作成・状態変更・実行を検証して適用します。選定だけでTaskを完了にしない。実装とレビューの記録の意味は#73、モデル指定と実際に使用したモデルの記録は#59、選定用の情報収集は#60、過去の性能実績の集計は#67が担当する。

## 入力と出力の全体像

両方向とも、受け渡すJSONの最上位の項目を同じ書式で示す。ここでは何の情報を渡すかを説明し、型・入れ子・省略条件は詳細仕様で定義する。

### Rustから監督Codexへ渡す入力

| 項目 | 何を伝えるか |
| --- | --- |
| `schema_version` | 入力形式のバージョン |
| `request_id` | 今回の選定依頼のID |
| `captured_at_ms` | Rustが入力を作成した時刻 |
| `task` | 作業の目的・制約と、今回選ぶ担当 |
| `providers` | 実行先とモデルの候補、利用可否・制限・使用量・過去実績 |
| `current_attempts` | 同じ作業でこれまでに行ったモデル実行の記録 |

候補や利用量を監督Codexに想像させず、Rustが収集した情報を渡す。[入力の定義](model-selection-spec-reference.md#入力の定義)から、各項目の入れ子へ進める。

### 監督CodexからRustへ返す出力

| 項目 | 何を伝えるか |
| --- | --- |
| `schema_version` | 出力形式のバージョン |
| `request_id` | どの選定依頼への返答か。入力と同じID |
| `assignments` | 要求された担当ごとに選んだ実行先・モデル・選定理由 |

選定結果の中で利用可否や使用量を書き換えない。[出力の定義](model-selection-spec-reference.md#出力の定義)に、最上位と担当ごとの結果を分けて記載する。

## 選定結果を実行する前に確認すること

Rustは、返された結果が今回の依頼に対応するか、必要な担当が過不足なく選ばれているか、候補と能力の条件を満たすか、現在の利用可否・予算・安全条件に反しないかを確認する。選定理由がもっともらしくても、この確認を省略しない。

実行を制限する上限（`hard`）の残量が不明なら、情報を再取得する。再取得後も不明または不足していれば、実行を許可しない。比較の参考情報（`advisory`）は不明でも、その理由を監督Codexに伝えて扱う。正確な確認項目とエラーは[実行前の確認規則](model-selection-spec-reference.md#rustが行う検証)に従う。

レビュー担当を選べることは、レビューを常に必須とする意味ではない。監督Codexが必要な担当だけを要求する。モデルを選んだ理由と、再試行やレビュー指摘への修正を行う理由は別に記録する。履歴分類の条件は[履歴設計](implementation-review-model.md#守る規則)に従う。

## 未確定事項と実装状況

[詳細仕様の未確定事項](model-selection-spec-reference.md#未確定の送信形式)には、一部の項目の省略とnull、状態・レビュー結果の文字列表現、結果不明の検証要約が残っている。これらを型案や例から推測して実装しない。[統合設計の再開条件](operation-service-integration-design.md#説明の補足と仕様の確定を分ける)も満たすまで、製品統合実装は再開しない。

## 後続実装への適用順

1. Issue #58 で担当とレビュー結果をドメインと記録用DBのどこへ保持するか決める。
2. Issue #59 で `ModelChoice` と実際に使用した Model を Provider / Attempt / Ledger へ接続する。
3. Issue #60 で出どころと確認時刻を持つ観測値、使用量、実行履歴の要約を収集する。性能実績の集計は Issue #67 が担当する。
4. Issue #61 で既存 `PlannerRequest` / `PlannerDecision` をこの入力／出力へ拡張し、Rust 側検証を実装する。

各Issueは共通の項目を実行先固有の形式へ置き換えず、取得できない項目は`unknown`として
保持する。仕様の互換性を壊す変更は `schema_version` を上げ、入力と出力を同時に更新する。
