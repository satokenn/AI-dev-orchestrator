# 開発支援システムの全体像

## このシステムで何をしたいのか

利用者がIssueや作業の要求を伝えると、監督役のCodexが実装担当モデルへ仕事を依頼し、変更内容と検証結果を見て、修正やPR公開へ進めるためのシステムである。

この文書を最初に読む。ここでは「誰が判断するか」「誰が実行するか」「設定を誰が用意するか」を説明する。以下は目標とする構成であり、すべてが実装済みという意味ではない。現行CLIの利用方法は[README](../README.md)を参照する。

## 登場人物と用語

| 名前 | このプロジェクトでの意味 |
| --- | --- |
| 利用者 | 作業の目的・制約を伝え、仕様やPRをレビューする人 |
| 監督Codex | 利用者の要求を読み、担当モデルや次の操作を選ぶAI。実装担当への指示も作る |
| Provider（実行先） | モデルを呼び出すための接続先・実行方法。例はCodex CLI。Modelはその実行先で使うモデルの名前 |
| MCP | 監督CodexからRust側へ、名前と入力が決まった操作を依頼するための通信方法 |
| Operation Service（操作を実行する共通処理） | 依頼を検査し、モデル実行・検証・公開を進め、結果を記録するRust側の処理 |
| Task（作業） | 一つの要求と、その要求に対する実行・検証・判断をまとめる単位 |
| Attempt（モデル実行） | モデルへ一回仕事を依頼した記録。再実行は別のAttemptになる |
| Artifact（保存済みの変更内容） | 後から検証・レビュー・公開できるよう、Gitの内容を固定して保存した成果物 |
| Validator（機械検査） | ビルドやテストなど、指定されたコマンドで成果物を確認する処理 |
| Ledger（記録用DB） | 作業、モデル実行、成果物、検証、判断などを保存するSQLite DB |

## 一つの作業が進む流れ

1. **利用者が目的を伝える。** 監督Codexが要求と制約をTaskとして登録する。
2. **監督Codexが担当を選ぶ。** 実行先、モデル指定、実装やレビューなどの役割、入力のコード、指示をRust側へ渡す。利用者が指定した制約があれば、その範囲で選ぶ。
3. **Rust側が実行できるか確認する。** 登録済みの実行先か、許可された作業場所か、モデル指定を確認できるかなどを検査し、受付と実行結果を記録する。
4. **変更内容を保存して確認する。** 監督Codexが必要なテストやAIレビューを依頼し、結果を見て採用か修正かを判断する。モデルの正常終了だけでは、コードの正しさや作業の完了は確定しない。
5. **条件を満たした成果物を公開する。** Rust側が採用判断、必要な検証、秘密情報の検査を照合してDraft PRを作り、公開したコミットのCI結果を記録する。
6. **監督Codexが完了を依頼する。** Rust側が同じ成果物に対する記録と未終了処理を確認し、条件を満たした場合にTaskを完了にする。

修正する場合は、保存済みの成果物を次のモデル実行へ渡す。レビュー実行は任意であり、ここに書いた流れから自動レビューや自動マージを追加するものではない。

## 操作の依頼と、起動時の設定は別のもの

**操作ごとの指定は監督Codexが渡す。** たとえば「登録済みのCodex CLIを使い、指定したモデルでこのコードを修正する」という依頼である。MCPの受け口が別の実行先を選び直すことはない。

**実行を許可する設定は、Rustサーバーを起動する側が用意する。** サーバーを組み立てるプログラムが、登録する実行先、許可する検査コマンド、秘密情報の検査処理、GitHubとの接続処理などをServiceに渡す。「注入」は、このように処理や設定を引数として渡すことを指す。監督Codexが送る操作の入力で、許可設定を差し替えることはできない。

統合設計で使っていた `trusted host` は、この**Rustサーバーを組み立てて起動する側**を指す。MCPの用語であるHost（監督Codexを動かすAIアプリケーション）とは区別する。「trusted」という語だけで安全性が保証されるわけではなく、操作の依頼者が変更できない設定を使う、という境界を表している。

モデル指定には二つの方式がある。`named` はモデル名を指定する方式、`provider_default` は実行先の既定モデルを使う方式である。モデル名を指定したときは、Rust側が起動前にその名前を確認できなければ拒否する。**その確認に使うモデル情報を実際に取得する本番処理は、今回の統合設計ではまだ提供していない。** 「設定を渡す方式が決まった」と「必要な設定や取得処理がすでに揃った」は別である。詳しい不足時の扱いは[統合設計の設定節](operation-service-integration-design.md#設定と不足時の扱い)を参照する。

## 詳細で繰り返し使う言葉

下記は日本語の説明と、コードや操作の入力に出てくる名前の対応である。実際の入力値や識別名は翻訳しない。

| 日本語の呼び方 | 詳細仕様での名前 | 意味 |
| --- | --- | --- |
| 処理の受付・進行記録 | operation | 長時間の操作を追跡する記録。モデル実行以外に、検証・公開・取消・CI待機もある |
| 更新番号 | revision | Taskの変更を検出する番号。古い情報に基づく変更要求を拒否するために使う |
| 同じ依頼の再送で処理を重ねないこと | 冪等性 | 受付済みの依頼をもう一度受けても、元の受付結果を返す |
| ある時点で固定した情報 | snapshot | 後から情報が増えても、当時の入力・対象を再確認できる記録 |
| 実行を許可する規則 | policy | 起動側が設定する制約。モデルによる採用判断とは別のもの |
| 過去の検証や判断の記録を指す情報 | EvidenceRef | 成功したという自己申告ではなく、保存済みの記録の識別子 |
| 実装・レビュー・調査の担当 | role | `implementer`（実装）、`reviewer`（レビュー）、`explorer`（調査）など |
| 開始時点のコード / 保存済み成果物 | BaseInput / ArtifactInput | 前者は指定したGitコミットから開始し、後者は保存済み成果物から開始する |
| Gitで固定したファイル一式 / 保持用の名前 | tree / ref | 前者が内容、後者がその内容をGit内に保持するための参照。作業フォルダとは別 |
| 一括保存 | transaction | 複数のDB変更を全部保存するか、全部取り消すかの単位 |
| 実行を担当する処理 | worker | 受付後に長時間の操作を進めるスレッド。独自に次の仕事を選ぶAIではない |
| 続きの取得位置 | cursor | 履歴を分けて読むためにサーバーが返す値。利用者は中身を解釈せず、次の取得へ渡す |
| 結果不明で確認が必要な状態 | recovery_required | 停止・外部処理の効果・保存結果を確認できない状態。成功や未実行と推測して再実行しない |

## 実装上の責務

目標構成では、監督Codexが判断し、Rust側が依頼の検査・実行・記録を担当する。現在のCLI内部にある`CodexPlanner`を主経路として拡張する方針ではない。

```text
利用者 → 監督Codex → MCPの受け口 → Rustの共通操作処理
            ↑                          ├─ 記録用DBと許可条件の検査
            └──── 結果・履歴 ──────────┤─ 作業場所と保存済み成果物
                                       ├─ モデルの呼び出し
                                       ├─ テスト等の機械検査
                                       └─ GitHub公開とCIの確認
```

| 担当 | 行うこと | 境界 |
| --- | --- | --- |
| 監督Codex | 要求を解釈し、実行先・モデル、再試行・レビューの要否、成果物の採否、完了要求を判断する | 観測された状態・使用量・CI結果を書き換えたり、許可条件を迂回したりしない |
| Rustの共通操作処理 | 依頼と更新番号を検査し、状態変更、排他、予算・安全条件の検査、実行、保存、結果返却を行う | 次の仕事やモデル、成果物の採否、作業完了を自発的に決めない |
| モデルの実行先 | 指定されたモデルを呼び出し、入出力・使用量を観測する | 作業全体の成功を判定しない |
| 機械検査 | 指定された成果物に指定の検査を行い、結果を返す | 要求の解釈や内容の意味をレビューする役割ではない |
| GitHub接続処理 | 指定された成果物を公開し、指定されたコミットのCIを観測する | 作業完了やマージを判断しない |

**モデル実行が正常終了しても、作業全体の完了ではない。** 機械検査、AIレビューの結果、監督Codexの採用判断、公開・CI、作業完了を、それぞれ同じ成果物に結び付けた別の事実として残す。記録の厳密な意味は[ドメインモデル](domain-model.md)を参照する。
